# IT correction request and reopening

This feature is separate from the student-confirmation proposal in #109/#179. It sends no email and does not change student credentials. A requester with a current, scoped information or photo review assignment may request correction only while that track is `LOCKED`. An assigned `IT_CORRECTION` reviewer in the same graduate scope may decide it. The requester cannot decide their own request.

`POST /api/admin/review-tracks/:trackId/correction-requests` takes `{ expectedVersion, operationId, reason }`. `GET /api/admin/correction-requests?status=PENDING&page=1` provides the assigned IT queue. `POST /api/admin/correction-requests/:id/decisions` takes `{ expectedVersion, operationId, decision: "APPROVE" | "REJECT", reason }`; a rejection requires a reason, approval has no reason. The browser never supplies an actor ID or capability. Every write checks the authenticated assignment, source cycle, exact version, and allowed stage again inside a transaction. Reusing an operation ID with different content returns 409.

The request references the exact locked information revision or photo pair and leaves its track locked. The database permits one pending request per track. A rejection records the IT reason and leaves the lock in place. Approval records the decision, moves the track to `DRAFT`, and creates a **new** baseline revision or pair with a `REOPENED` event. The old locked revision, pair, events, and request remain. The maker must save an information change or replace a photo before submitting the reopened review to QC. It must then pass QC and moderator review again before becoming completed.

Two migrations add the `REOPENED` enum values, then the correction table and transition constraints. The table has restrictive foreign keys, a partial unique index for pending requests, a shape constraint, and a trigger preventing deletion or later mutation of decided requests. Existing graduate rows are not rewritten by the migration. Follow the repository's protected backup and restore procedure, reconcile the deployed migration history, and apply the migrations to an **isolated** PostgreSQL database before deploying any correction endpoints. A live database was not accessed while preparing this PR.

Required integration checks on that database: unauthorized reads and writes; scoped access; duplicate/pending requests; changed request ID; same-user IT decision; stale versions; rejection remains locked; approval creates a distinct revision/pair while preserving the old lock; maker change required; QC and moderator reapproval; concurrent IT decisions; backup/restore; and old registration, booking, and image reads. The local TypeScript build and contract tests do not substitute for these checks.
